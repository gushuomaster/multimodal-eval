# 多模态大模型测评平台 MVP 完成总结

汇报日期：2026-10-09

汇报范围：基于 EvalScope 建设的自有多模态大模型测评平台 MVP

当前结论：MVP 约定的两个阶段已经完成，可以进入与后端、前端联调阶段。

## 一、项目目标

本项目使用 EvalScope 作为底层评测引擎，目标不是只完成一次模型测试，而是形成一条可以持续使用的多模态业务测评流程：

1. 使用客户自己的文字、单图和多图数据发起模型测评。
2. 判断模型返回的结构化 JSON 是否满足业务要求。
3. 由后端通过命令行参数启动一次独立的 Docker 评测任务。
4. 在任务执行期间向后端输出日志。
5. 在任务结束后，将状态、模型回答、逐条评分和汇总报告写入指定目录。

本轮 MVP 只完成以上最短闭环，不包含前端页面、HTTP 服务、并发任务平台和生产安全加固。

## 二、MVP 已完成功能

### 1. 客户多模态数据接入

已建立 `customer_multimodal_v1` 数据集，支持：

- 使用本地 JSONL 作为测评数据。
- 每条数据包含文字问题以及一张或多张图片。
- 每条数据设置结构化标准答案。
- 检查样本编号、字段类型、媒体路径和标准答案是否合法。
- 使用不同文件作为不同数据子集。

项目自带的示例数据位于：

```text
custom_eval/multimodal/customer_v1/example.jsonl
```

示例图片位于：

```text
custom_eval/multimodal/images/
```

### 2. 结构化业务评分

平台已经可以对模型返回的 JSON 做业务级评分，而不只是检查回答是否能解析。

已支持：

- JSON 格式检查。
- JSON Schema 结构检查。
- 字符串、整数、小数、布尔值和 `null` 比较。
- 字段级正确率 `field_accuracy`。
- 整条回答正确率 `overall_accuracy`。
- 整条业务命令是否合格 `overall_command_correct`。
- 数值绝对误差范围。
- 关键字段设置。
- 缺失字段、类型错误、数值错误和误差超限明细。
- 拒绝字段权重、相对误差和文本自动归一化等尚未实现的配置，避免静默忽略。
- 拒绝客户字段名与平台固定指标名冲突。

这些核心业务指标已经登记为正式平台指标，可以进入汇总报告。

### 3. 模型接口调用

平台可以通过 OpenAI-compatible 接口调用模型。一次任务可以传入：

- 模型名称。
- 模型接口地址。
- API Key。
- 生成参数。
- 最大测评样本数。

同时保留 `mock_llm` 模式，用于不调用付费接口时验证完整执行链路。`mock_llm` 的分数不代表真实模型能力。

### 4. 后端命令行启动

后端调用以下入口启动任务：

```text
python scripts/mvp/run_container.py [参数]
```

后端至少传入：

| 参数 | 作用 |
| --- | --- |
| `--data-dir` | 宿主机数据根目录，必须已经存在 |
| `--output-dir` | 本次任务输出目录，不存在时自动创建 |

真实模型任务通常还需要：

| 参数 | 作用 |
| --- | --- |
| `--eval-type openai_api` | 使用真实 OpenAI-compatible 模型接口 |
| `--model` | 模型服务识别的模型名称 |
| `--api-url` | 模型接口地址 |
| `--api-key` | 模型接口密钥 |

其他参数均有默认值，后端不需要设置 PowerShell 编码变量、拼接 Docker 命令或手工修改 YAML。

### 5. Docker 执行

已完成独立 MVP 镜像和容器启动流程：

```powershell
docker build -f docker/mvp/Dockerfile -t multimodal-eval:mvp .
```

运行方式为“Windows 宿主机 + Docker Desktop/WSL2 + Linux 容器”。Linux 只存在于 Docker 内部，前端和后端仍运行在 Windows 上。

每次任务会完成以下操作：

1. 读取默认配置模板。
2. 使用本次命令行参数生成新的运行配置。
3. 保持默认模板不变。
4. 将数据目录只读挂载到容器。
5. 将结果目录可写挂载到容器。
6. 在前台启动容器并实时转发日志。
7. 将容器退出码返回给后端。
8. 无论成功或失败，都尽量生成机器可读状态文件。

### 6. 结果输出

输出目录由后端通过 `--output-dir` 指定。固定结构为：

```text
<output-dir>/
  runtime/task_config.yaml
  run_status.json
  logs/eval_log.log
  configs/
  reports/<model_id>/customer_multimodal_v1.json
  reviews/<model_id>/customer_multimodal_v1_example.jsonl
  predictions/<model_id>/customer_multimodal_v1_example.jsonl
```

文件用途：

| 文件 | 用途 |
| --- | --- |
| `run_status.json` | 判断任务成功或失败，并定位本次产物 |
| `runtime/task_config.yaml` | 保存本次实际生效的运行参数 |
| `logs/eval_log.log` | 保存执行日志 |
| `reports/...json` | 保存汇总评分 |
| `reviews/...jsonl` | 保存每条样本的评分和错误原因 |
| `predictions/...jsonl` | 保存模型原始回答 |

后端应等待启动进程结束后，优先读取 `run_status.json`，再按照其中的相对路径读取结果，不需要硬编码模型目录。

## 三、默认配置和数据路径

默认配置模板：

```text
configs/mvp/customer_multimodal_v1.yaml
```

默认数据子目录：

```text
custom_eval/multimodal/customer_v1
```

Docker 会把命令行传入的宿主机 `--data-dir` 挂载为容器内的 `/eval/data`。因此默认配置中的：

```text
/eval/data/custom_eval/multimodal/customer_v1
```

对应的是宿主机项目目录下的：

```text
<项目根目录>/custom_eval/multimodal/customer_v1
```

## 四、标准执行流程

```text
前端填写评测参数
        ↓
后端接收并校验参数
        ↓
后端以参数数组启动 run_container.py
        ↓
启动器生成本次 runtime 配置
        ↓
Docker 容器执行 EvalScope 评测
        ↓
标准输出持续返回执行日志
        ↓
进程结束并返回退出码
        ↓
后端读取 run_status.json 和结果 JSON/JSONL
        ↓
前端展示状态、分数和逐条结果
```

前端不直接拼接 PowerShell 命令，也不直接操作 Docker。Docker 和命令行启动器属于后端执行层。
