# 多模态大模型测评平台阶段进展汇报

汇报日期：2026-10-08

汇报范围：基于 EvalScope 建设的自有多模态大模型测评平台

当前阶段：底层评测能力验证与客户业务评分能力建设

## 一、项目为什么启动

我们最开始引入 EvalScope，不是为了只测试某一个模型，也不是为了单独开发一个评分脚本。

项目的核心目标是：

> 以 EvalScope 作为评测底座，验证它能否支撑我们自己的多模态大模型测评平台，并建立一套可以持续增加模型、数据、评分规则和测评任务的开发基础。

选择这一方案的原因是，模型调用、数据读取、任务执行、结果保存、分数汇总和报告生成等通用能力已经由 EvalScope 提供。我们的开发重点应放在客户数据、业务规则和平台管理能力上，而不是重新开发一套评测引擎。

## 二、当前总体结论

目前已经证明：

- EvalScope 可以作为自有多模态测评平台的底层评测引擎。
- 文本、单图和多图请求可以通过真实模型接口执行。
- 客户自定义多模态数据可以接入并形成标准测评结果。
- 平台可以对结构化 JSON 回答进行字段级和整条命令级评分。
- 评测结果可以保存为明细、汇总数据和 HTML 报告。

但当前成果仍属于“可持续开发的评测底座和功能原型”，还不是可以直接交付给业务用户使用的完整平台。

当前状态可以概括为：

| 状态 | 含义 |
| --- | --- |
| 已完成 | 功能已经实现，并有测试或实际运行结果证明可用 |
| 部分完成 | 主体功能可用，但仍有明确问题需要收口 |
| 尚未开发 | 我们自己的平台还没有对应功能 |
| 尚未充分测试 | 已有代码或 EvalScope 已有能力，但未完成我们的接入和验证 |

## 三、已完成功能

### 1. 模型接口接入

平台已经能够通过 OpenAI-compatible 接口调用模型，不需要为每个兼容模型重新编写请求程序。

已完成：

- API 地址、密钥和模型名称可通过配置传入。
- 密钥不会硬编码到项目代码和测试数据中。
- 模型请求、回答接收和错误记录链路已经跑通。
- MiniMax 文本模型和视觉模型均完成实际接口验证。

实际结果：

- MiniMax-M2.7 文本测评：请求 3 条，成功 3 条。
- MiniMax-M3 多模态测评：请求 2 条，成功 2 条。

当前结论：模型接口基本链路已经具备，可以继续接入其他 OpenAI-compatible 模型。

### 2. 文本模型测评

平台已经能够读取文本题目、调用模型、计算分数并保存结果。

已完成：

- 使用 GSM8K 小样本完成文本接口验证。
- 模型输出、样本级结果、汇总分数和 HTML 报告均已生成。
- 已确认评测结果能够落盘，便于后续查看和复跑。

当前结论：文本评测执行链已经跑通，但当前只属于小规模连通性验证，不代表已经完成正式的大规模模型能力评估。

### 3. 单图和多图输入

平台已经能够把本地图片和文字问题一起发送给视觉模型。

已完成：

- 单张图片输入。
- 多张图片输入。
- 图片数量和顺序保持验证。
- 本地图片路径转换为模型请求所需的多模态消息。
- 模型回答和评测结果保存。

当前结论：正式项目最关键的“文本 + 多图”输入链已经验证可行。

### 4. 客户自定义数据接入

平台已经建立 `customer_multimodal_v1` 客户数据集，可以使用客户自己的问题、图片和标准答案进行测评。

已完成：

- 支持本地 JSONL 数据。
- 支持单图和多图样本。
- 支持每条样本设置标准答案。
- 检查样本编号、字段名称和答案类型是否合法。
- 拒绝数组、嵌套对象、无穷值等当前业务不接受的标准答案。
- 保存样本编号、期望字段和评分明细，便于定位问题。

当前结论：已经摆脱只能使用公开数据集的限制，可以围绕客户业务构建自己的测评集。

### 5. 结构化业务评分

平台已经能够判断模型返回的 JSON 是否符合业务要求，而不仅仅判断“是不是 JSON”。

已完成：

- 严格检查 JSON 格式。
- 拒绝 `NaN`、`Infinity`、非对象回答和其他非法结果。
- 支持字符串、整数、小数、布尔值和 null。
- 布尔值不会被误判为数字，例如 `true` 不等于 `1`。
- 字符串默认严格比较，不自动忽略大小写、空格或标点。
- 支持给数字字段设置绝对误差范围。
- 支持指定关键字段。
- 支持统计字段正确率。
- 支持判断整条业务命令是否合格。
- 支持 JSON Schema 对必填字段、类型、范围和额外字段进行检查。
- 将缺失字段、类型错误、值错误和误差超限保存到评测明细。

MiniMax-M3 两条实际样本结果：

| 样本 | 字段正确率 | 整条命令是否合格 |
| --- | ---: | ---: |
| 单图 | 66.67% | 否 |
| 多图 | 100% | 是 |
| 汇总 | 83.33% | 50% |

当前结论：结构化业务评分主体已经完成，但仍有三项合并前问题，详见“部分完成功能”。

### 6. 结果保存与报告

平台已经能够自动保存一次测评产生的主要结果。

已完成：

- 保存运行配置。
- 保存模型原始回答。
- 保存每条样本的评分和错误原因。
- 保存汇总分数。
- 生成 JSON 报告。
- 生成 HTML 报告。
- 保存解析错误数量等补充诊断信息。

当前结论：结果已经可以供研发排查和人工查看，但还没有形成面向业务用户的报告管理产品。

### 7. 持续开发与质量保障

项目已经不再是一次性测试脚本，而是具备持续开发基础的源码工程。

已完成：

- 保留官方 EvalScope 基线，便于后续跟踪上游变化。
- 使用 `develop` 和独立功能分支开发。
- 使用隔离 worktree，避免不同任务互相污染。
- 为客户数据、评分规则、报告和注册机制建立自动化测试。
- 结构化评测相关测试累计 111 项通过。
- 核心冒烟测试通过。
- 代码导入边界检查通过。
- 变更文件格式、编码、换行和密钥扫描通过。

当前结论：已经建立继续增加功能所需的基本工程纪律和回归保障。

## 四、部分完成功能

### 1. 业务评分指标还没有完全成为平台正式指标

字段正确率和整条命令正确率已经能够计算，也能进入报告。

目前的问题是，EvalScope 报告系统仍把这两个新分数当作“附加数据”，没有把它们当成可以正式比较高低的评分指标。

影响：

- 报告中可以看到数值。
- 但平台还不能完整表达“分数越高越好、取值范围为 0 到 1”等正式含义。
- 运行时会出现指标尚未登记的提醒。

需要完成：在平台的指标登记表中加入这两个业务指标，并补充报告级测试。

### 2. 特殊字段名可能与平台分数名称冲突

如果客户标准答案中存在名为 `field` 的字段，它生成的字段分数可能与总体字段正确率使用同一个名称。

影响：个别合法业务字段可能被总体分数覆盖。

需要完成：统一检查客户字段名与平台固定分数名是否冲突，并在数据加载时明确报错。

### 3. 尚未支持的评分配置需要明确拒绝

当前只正式支持绝对误差和关键字段。字段权重、相对误差和文本自动归一化尚未实现。

目前的问题是，部分未支持配置可能被系统忽略，而不是立即提醒用户。

影响：用户可能误以为某项配置已经生效，实际仍按默认规则评分。

需要完成：发现未支持配置时直接报错，并明确说明当前支持范围。

### 4. 中文文档尚未生成

英文说明和自动生成页面已经更新，但中文翻译需要额外翻译接口凭据。

当前中文页面仍是英文回退内容，不影响评测运行，但影响中文用户阅读。

## 六、尚未充分测试的功能

- 长时间运行不会出现资源泄漏或结果丢失。

## 七、当前主要风险

| 风险 | 当前影响 | 建议 |
| --- | --- | --- |
| 新业务分数尚未正式登记 | 报告能显示，但不能作为完整正式指标使用 | 优先完成指标登记和报告验证 |
| 业务字段名可能冲突 | 极少数数据可能被错误评分 | 加载数据时直接拦截冲突字段 |
| 未支持配置可能被忽略 | 用户可能误判评分规则已生效 | 对未知配置立即报错 |
| 测试样本数量很少 | 只能证明链路可用，不能证明模型真实水平 | 建设正式数据集后扩大评测规模 |
| 目前主要依赖单一厂商接口 | 无法证明跨厂商兼容性 | 增加至少一个其他厂商回归模型 |
| 结果以文件为主 | 前端尚无统一读取入口 | MVP 阶段约定容器输出目录、报告 JSON 和样本明细的返回方式 |
| 尚无权限与密钥管理 | 不适合多人生产使用 | 在平台化前完成安全设计 |

## 八、当前 MVP 范围与后续顺序

当前 MVP 只包含前两个阶段。第三阶段的测评能力扩展不属于本次 MVP 范围，不作为当前交付的前置条件。

### 第一优先级：完成当前结构化评分收口

目标：让现有客户测评能力达到可以合并和持续使用的状态。

建议完成：

1. 正式登记字段正确率和整条命令正确率。
2. 修复业务字段名与平台分数名冲突。
3. 对未支持评分配置直接报错。
4. 补充测试并重新完成独立审查。
5. 推送功能分支，经确认后合并到 `develop`。

### 第二阶段：容器化测评运行闭环

目标：前端提交测评参数，由后端启动容器；容器内运行本项目的 EvalScope 命令行程序，并把日志和结果交回平台。

最小范围：

1. 将项目及运行依赖封装为可运行的镜像。
2. 前端提交模型、数据集、评分规则等任务参数；后端校验参数并转换为容器启动参数。
3. 后端通过命令行启动容器，容器内执行 `evalscope eval`。
4. 将运行日志输出到标准输出/错误流，供后端转发给前端展示，同时保留日志文件。
5. 挂载评测输入数据及图片，并将结果目录挂载到容器外可读取的位置。
6. 任务结束后返回退出状态、报告 JSON 路径和样本明细路径。

当前 MVP 不包含模型管理后台、数据集管理后台、复杂任务队列、模型对比看板、账号权限和多机调度。API 密钥应通过后端安全注入容器，不应由浏览器直接传入命令行或写入日志。

### MVP 之后：按业务需要扩展测评能力

以下能力仅作为后续可选方向，不纳入本次 MVP 验收：

1. 自由文本评分。
2. 公开视觉基准。
3. 多轮和长上下文。
4. RAG、幻觉和指令遵循。
5. 鲁棒性和稳定性。
6. 安全测试。
7. Agent 和工具调用测评。

后续确有业务需求时，再定义问题、评分规则和验收数据，优先复用 EvalScope；只有现有能力无法满足时，才增加自有扩展。

## 九、阶段结论

目前已经完成的不是完整平台，而是完整平台最关键的第一层基础：

```text
模型与多模态数据
        ↓
执行测评任务
        ↓
按业务规则评分
        ↓
保存明细和汇总报告
```

这一阶段已经证明 EvalScope 作为底层评测引擎的路线可行，也证明客户自定义多模态数据和业务评分可以接入。

下一步先完成结构化评分收口，再实现前端提交参数、后端启动容器、容器内运行测评、日志回传和结果文件读取的最小闭环。其他平台管理功能和新测评方向均不作为当前 MVP 的前置要求。

当前项目定位：

> 已完成可持续开发的多模态评测底座和业务评分原型，尚未形成面向业务用户的完整测评平台。
